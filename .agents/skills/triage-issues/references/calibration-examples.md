# Triage calibration — worked examples

These 40 scenarios are the source data the `triage-issues` skill's decision procedures were derived from. Each was rated
independently on **effort** (`size::*`) and **priority** (`priority::*`) by the repo maintainer, with a one-line
rationale for each rating. Read this file when a new triage case doesn't cleanly match a rule in `SKILL.md` — find the
closest precedent here before inventing a new heuristic.

Two pairs are deliberately contrastive (same fix, different context) — #5/#33 vs #34, and #15 vs #16 — because the
difference between the two ratings _is_ the rule.

## Confirmed calibration notes

- **#4 vs #12** (both "big blast radius, simple config, easy rollback" — Omni Dex TTL rated `L`, DNS resolver rated
  `M`): confirmed as a **gut-feel wobble**, not a rule. Don't encode "Omni/trust-root systems always outrank DNS-like
  broad systems by a full band" as a hard rule — treat trust-root vs. merely-broad as a soft tie-breaker only (see
  SKILL.md).
- **#35 vs #39** (both routine/periodic upgrades — OpenBao Helm patch bump rated `high`, Talos/Kubernetes upgrade rated
  `medium`, despite #35's own stated rule that periodic bumps default `low`): confirmed intentional — **"routine" is not
  a flat priority floor.** It scales with how critical/security-relevant the thing being bumped is. A leaf dependency's
  routine bump floors low; a core secret-store or cluster-runtime component's routine bump floors medium.

## Extending this file

When a real triage case doesn't fit an existing rule cleanly, resolve it with the user and add a row here (or a new
contrastive pair) rather than only updating `SKILL.md` — the rules in `SKILL.md` should always be traceable back to a
concrete precedent in this file.
