## Procedure BKP-20260805-00: Restore a Velero-backed PVC on a GitOps-managed cluster

This procedure restores a PersistentVolumeClaim from a Velero (Kopia fs-backup) backup, on a cluster where a controller
(StatefulSet, or ArgoCD/Kustomize for a Deployment) already owns and reconciles the target Pod. That ownership is
exactly what breaks Velero's default restore flow, and no combination of Velero's own documented flags works around it —
the workaround is a sequence of operations, not a flag. This was discovered and validated end to end against
`lungmen.akn`'s `jellyfin` app; see the Complete Example below.

### Technical framework and conventions

Velero's `PodVolumeRestore` controller only injects its `restore-wait` init container into a Pod it creates itself —
that init container is what blocks the app container from starting until the volume data is actually written. Any Pod
already managed by a live controller breaks this: the controller re-creates the Pod on its own before Velero's restore
ever runs, the injection never happens, and the `PodVolumeRestore` stalls silently in its `New`/empty phase — no error,
nothing but `status.progress` staying at zero to signal it's stuck. This is
[velero-io/velero#9461](https://github.com/velero-io/velero/issues/9461), closed upstream as "by design" — Velero
expects a stable environment with nothing else reconciling the target resources during a restore.

This follows directly from the mechanism above: remove the live controller and the bound PVC before restoring, so Velero
_creates_ both fresh instead of patching existing ones. A Create isn't subject to the immutable-field restrictions that
sink the documented `existingResourcePolicy: update` workaround, and with no controller present, nothing competes to
delete the Pod Velero creates for it. The controller resource is restored in the same operation (it's backed up as part
of the same namespace), so once the `PodVolumeRestore` completes and the Pod is `Ready`, the freshly-restored controller
takes over normal reconciliation — by then actual and desired state already match, so there's no conflict left to have.
See Known issues below for two workarounds that look plausible but don't work (`existingResourcePolicy: update`, scaling
to 0 first).

> [!IMPORTANT]
>
> Every app in this repo is ArgoCD/GitOps-managed (see AGENTS.md). `selfHeal` on the app's ArgoCD `Application` is
> exactly the mechanism this procedure needs to be absent while it runs — if it's left on, ArgoCD detects the Step 3
> deletion as drift and can recreate the controller before Velero's restore gets to it, reproducing the same stuck
> `PodVolumeRestore` this procedure exists to avoid. There is no separate ArgoCD "maintenance mode" for an
> `Application`; disabling its sync policy (`argocd app set <app> --sync-policy none`) is the mechanism, and it applies
> to any procedure in this repo that manually deletes or edits a resource ArgoCD reconciles, not just this one. Step 3
> below disables it; Step 7 restores it to whatever it was before.

> [!CAUTION]
>
> This procedure deletes the target PVC. Check `persistentVolumeReclaimPolicy` on its bound PV before starting (Step 1)
> — if it's `Delete` rather than `Retain`, the underlying volume is destroyed immediately and irreversibly outside of
> this restore path. Don't assume a cluster-wide `Retain` policy applies retroactively to a PV provisioned before that
> policy existed — verify the specific PV.

### Prerequisites

Before starting, ensure `kubectl`, the `velero` CLI, and the `argocd` CLI are installed and configured locally — this
procedure runs `velero` directly, not via `kubectl exec` into the in-cluster `velero` Deployment.

You must also have:

- `kubectl` access to the target cluster with permission to delete the owning workload (StatefulSet or Deployment) and
  its PVC, and to create Velero `Restore` objects in the Velero namespace.
- `argocd` CLI access with permission to change the sync policy of the ArgoCD `Application` governing `$APP_NAMESPACE`.
- A completed Velero `Backup` covering the target workload, its PVC, and the underlying PV — a namespace-scoped backup
  is fine as long as it includes all three.
- A healthy `BackupRepository` (`kubectl get backuprepositories.velero.io -n $VELERO_NAMESPACE` → `Ready`).

> [!NOTE]
>
> `kubectl get backups`/`restores` (without the `.velero.io` suffix) can resolve to the wrong CRD if another operator
> also registers a short `Backup`/`Restore` kind — CloudNativePG does exactly this. Always use the fully-qualified
> `backups.velero.io` / `restores.velero.io` / `podvolumerestores.velero.io` / `backuprepositories.velero.io` names on a
> cluster running both.

### Required inputs

Export these once, then every command below can be copy-pasted as-is:

```sh
export VELERO_NAMESPACE=<namespace Velero itself is installed in>  # e.g. velero-system
export APP_NAMESPACE=<namespace the target app lives in>           # e.g. jellyfin
export ARGOCD_APP_NAME=<ArgoCD Application governing APP_NAMESPACE> # e.g. jellyfin
export WORKLOAD_KIND=<statefulset|deployment>                      # controller owning the target Pod
export WORKLOAD_NAME=<name of that workload>                       # e.g. jellyfin
export PVC_NAME=<PVC to restore>                                   # e.g. persistent-jellyfin-0
export BACKUP_NAME=<Velero Backup to restore from>                 # see below
export RESTORE_NAME=<name for the new Restore object>              # e.g. ${WORKLOAD_NAME}-restore-$(date +%Y%m%d%H%M%S)
```

Pick `BACKUP_NAME` as the most recent healthy backup for `APP_NAMESPACE` (filter
`kubectl get backups.velero.io -n $VELERO_NAMESPACE` by name prefix).

## Step 1 — Confirm the PVC's reclaim policy before touching anything

The PVC gets deleted in Step 3 either way — this check doesn't change any later step. It only tells you how destructive
that deletion is, so you know how much to trust the Backup in Required inputs before proceeding.

```sh
PV_NAME=$(kubectl get pvc -n $APP_NAMESPACE $PVC_NAME -o jsonpath='{.spec.volumeName}')
kubectl get pv "$PV_NAME" -o jsonpath='{.spec.persistentVolumeReclaimPolicy}{"\n"}'
# → Delete: deleting the PVC in Step 3 destroys the underlying volume for real, immediately. Proceed only if the
#   Backup in Required inputs is confirmed healthy and recent enough to accept that risk.
# → Retain: the PV survives PVC deletion as an orphan — lower risk, but doesn't change what Step 3 does.
```

## Step 2 — Verify the backup actually contains real data

```sh
kubectl get backups.velero.io -n $VELERO_NAMESPACE $BACKUP_NAME \
  -o jsonpath='{.status.phase}{"\t"}errors={.status.errors}{"\t"}warnings={.status.warnings}{"\n"}'
# → Completed	errors=	warnings=

kubectl get podvolumebackups.velero.io -n $VELERO_NAMESPACE \
  -l velero.io/backup-name=$BACKUP_NAME \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.phase}{"\t"}bytes={.status.progress.bytesDone}/{.status.progress.totalBytes}{"\n"}{end}'
# → one line per volume backed up, phase=Completed, bytesDone == totalBytes and > 0
```

## Step 3 — Disable ArgoCD sync, then delete the workload and the PVC

```sh
# Capture the current sync policy so Step 7 knows whether to restore it.
SYNC_POLICY_BEFORE=$(argocd app get $ARGOCD_APP_NAME -o json | jq -r '.spec.syncPolicy.automated // empty')
# → non-empty (e.g. {"prune":true,"selfHeal":true}) if automated sync was on; empty if it was already manual.

argocd app set $ARGOCD_APP_NAME --sync-policy none
# → confirms the sync policy is updated to manual

# Cascades to delete the Pod too — this is deliberate, not a side effect to work around.
kubectl delete $WORKLOAD_KIND -n $APP_NAMESPACE $WORKLOAD_NAME

# Destroys the volume immediately if Step 1 showed reclaimPolicy=Delete.
kubectl delete pvc -n $APP_NAMESPACE $PVC_NAME

kubectl get pod,pvc,$WORKLOAD_KIND -n $APP_NAMESPACE
# → nothing left matching WORKLOAD_NAME/PVC_NAME (other PVCs in the namespace, e.g. read-only
#   external shares, are untouched — this procedure only targets the one named PVC)
```

## Step 4 — Trigger the restore

```sh
velero restore create $RESTORE_NAME --from-backup $BACKUP_NAME
# → Restore request "<RESTORE_NAME>" submitted successfully.
```

> [!IMPORTANT]
>
> Do **not** add `--existing-resource-policy=update` here — with the workload and PVC already gone (Step 3), there's
> nothing left to conflict with, and that flag only matters for the broken patch-based path this procedure exists to
> avoid.

## Step 5 — Watch the restore and the volume-level progress separately

The parent `Restore`'s `itemsRestored` counts Kubernetes resources (workload, PVC, Pod, ...), not volume bytes — a
`Restore` can show `Completed` with all items restored while the actual data restore is still running or never started.
Track the `PodVolumeRestore` for the real signal.

```sh
kubectl get restore.velero.io -n $VELERO_NAMESPACE $RESTORE_NAME \
  -o jsonpath='{.status.phase}{" items="}{.status.progress.itemsRestored}/{.status.progress.totalItems}{"\n"}'
# → InProgress items=11/11   (resource-level restore already done; volume data may still be copying)
# → Completed items=11/11    (terminal)

kubectl get podvolumerestores.velero.io -n $VELERO_NAMESPACE \
  -l velero.io/restore-name=$RESTORE_NAME \
  -o jsonpath='{range .items[*]}{.status.phase}{" "}{.status.progress.bytesDone}/{.status.progress.totalBytes}{"\n"}{end}'
# → InProgress 566097972/1113847811   (byte-level progress — this is the real "is it stuck" signal)
# → Completed 1113847811/1113847811   (terminal, bytesDone == totalBytes)
```

> [!NOTE]
>
> If the `PodVolumeRestore` phase stays empty/unset for more than a minute or two with zero byte progress, the restore
> has hit the exact failure mode described in Technical framework and conventions above — the owning controller
> recreated the target Pod before Velero got to inject its `restore-wait` init container. Go back and confirm Step 3
> actually removed the workload (not just scaled it), and that nothing else in the cluster re-created a Pod matching the
> target name in the meantime.

## Step 6 — Verify at the application layer, not just Pod readiness

A Pod reaching `Ready` proves the container started — it does not prove the _restored_ data is what it's running on (a
stale or freshly-empty PVC binding by mistake would also reach `Ready`). Check application-level evidence.

```sh
# StatefulSet pods are deterministically named `$WORKLOAD_NAME-0`; for a Deployment, find the current
# pod name first: kubectl get pod -n $APP_NAMESPACE -l app=$WORKLOAD_NAME
kubectl get pod -n $APP_NAMESPACE $WORKLOAD_NAME-0
# → 1/1 Running

kubectl logs -n $APP_NAMESPACE $WORKLOAD_NAME-0 --tail=30
# → look for restored-state evidence specific to the app (existing user accounts, known config
#   values, library/collection names — anything that could only be present if the pre-loss data
#   actually came back, not just default/empty startup state)
```

## Step 7 — Re-enable ArgoCD sync

Only if `SYNC_POLICY_BEFORE` from Step 3 was non-empty — an app that was already on manual sync before this procedure
started should stay that way; this procedure isn't responsible for changing that decision.

```sh
if [ -n "$SYNC_POLICY_BEFORE" ]; then
  argocd app set $ARGOCD_APP_NAME --sync-policy automated --auto-prune --self-heal
  # → confirms the sync policy is back to automated. Adjust --auto-prune/--self-heal if
  #   $SYNC_POLICY_BEFORE showed different prune/selfHeal values than this repo's usual default (both true).
else
  echo "Sync was already manual before this procedure — leaving it as-is."
fi
```

## Complete Example: `jellyfin` on `lungmen.akn`

```sh
export VELERO_NAMESPACE=velero-system
export APP_NAMESPACE=jellyfin
export ARGOCD_APP_NAME=jellyfin
export WORKLOAD_KIND=statefulset
export WORKLOAD_NAME=jellyfin
export PVC_NAME=persistent-jellyfin-0
export BACKUP_NAME=jellyfin-20260805150447
export RESTORE_NAME=jellyfin-corruption-test3-20260805190312

# Step 1
PV_NAME=$(kubectl get pvc -n jellyfin persistent-jellyfin-0 -o jsonpath='{.spec.volumeName}')
kubectl get pv "$PV_NAME" -o jsonpath='{.spec.persistentVolumeReclaimPolicy}{"\n"}'
# → Delete (confirmed live — contradicts an earlier assumption that this PV had already moved to
#   Retain; a cluster-wide Retain storage-class change does not apply retroactively to PVs
#   provisioned before it)

# Step 3
SYNC_POLICY_BEFORE=$(argocd app get jellyfin -o json | jq -r '.spec.syncPolicy.automated // empty')
argocd app set jellyfin --sync-policy none
kubectl delete statefulset -n jellyfin jellyfin
kubectl delete pvc -n jellyfin persistent-jellyfin-0

# Step 4
velero restore create jellyfin-corruption-test3-20260805190312 \
  --from-backup jellyfin-20260805150447 --namespace velero-system

# Step 5 (final state reached)
# restore.velero.io: Completed items=11/11
# podvolumerestores.velero.io: Completed 1113847811/1113847811

# Step 6
kubectl logs -n jellyfin jellyfin-0 --tail=30
# → real restored user accounts present: "Alexandre NICOLAIE", "François NICOLAIE",
#   "Estelle SCHWEICHLER", "FireStick 4K - Salon" — confirms the actual pre-loss SQLite
#   config came back, not a fresh/empty database

# Step 7
if [ -n "$SYNC_POLICY_BEFORE" ]; then
  argocd app set jellyfin --sync-policy automated --auto-prune --self-heal
fi
```

## Quick verifications

- **Restore phase**: `kubectl get restore.velero.io -n $VELERO_NAMESPACE $RESTORE_NAME` → `Completed`
- **Volume data fully written**:
  `kubectl get podvolumerestores.velero.io -n $VELERO_NAMESPACE -l velero.io/restore-name=$RESTORE_NAME -o jsonpath='{.items[0].status.progress}'`
  → `bytesDone == totalBytes`, both non-zero
- **No silent patch failures**:
  `velero restore logs $RESTORE_NAME --namespace $VELERO_NAMESPACE | grep -i "patch attempt failed"` → no output
- **Pod healthy**: `kubectl get pod -n $APP_NAMESPACE $WORKLOAD_NAME-0` → `1/1 Running`
- **Application-level data present**: app-specific log/API check (Step 6) — do not skip this one
- **ArgoCD sync restored**: `argocd app get $ARGOCD_APP_NAME -o json | jq '.spec.syncPolicy.automated'` → matches
  `$SYNC_POLICY_BEFORE` from Step 3

## Known issues

### `existingResourcePolicy: update` does not solve the naive-restore failure

This documented Velero workaround does a JSON merge PATCH on existing resources, not a delete+recreate. Kubernetes
itself rejects the patch on the exact fields Velero needs to change —
`spec.initContainers: Forbidden: pod updates may not add or remove containers` for the Pod, and
`spec: Forbidden: spec is immutable after creation except resources.requests...` for an already-bound PVC. The `Restore`
object still reports `Completed`, just with warnings — nothing about the phase alone tells you the data was never
touched.

### Scaling the workload to 0 first doesn't work either

With desired replica count at 0, the controller deletes _any_ pod matching its name pattern the instant it appears —
including the one Velero's restore creates. Confirmed via a `SuccessfulDelete` event from the controller landing seconds
after the `PodVolumeRestore` is created; the PVR is then permanently orphaned, silently, exactly like the no-workaround
case.

### A previously-attempted restore left an orphaned `PodVolumeRestore` that blocks `kubectl delete`

If an earlier attempt used the scale-to-0 workaround (or was otherwise interrupted while its target pod got replaced),
the leftover `PodVolumeRestore` carries the finalizer `velero.io/pod-volume-finalizer`. Its controller's cleanup path is
gated behind the same pod lookup that's already broken for it, so it can never remove its own finalizer, and a normal
`kubectl delete` hangs indefinitely.

```sh
kubectl patch podvolumerestores.velero.io -n $VELERO_NAMESPACE <STUCK_PVR_NAME> \
  --type=merge -p '{"metadata":{"finalizers":[]}}'
kubectl delete podvolumerestores.velero.io -n $VELERO_NAMESPACE <STUCK_PVR_NAME>
kubectl delete restore.velero.io -n $VELERO_NAMESPACE <STUCK_RESTORE_NAME>
```

Also restore the workload's replica count back to what the backup expects before retrying with this procedure — a
mismatched desired count is what caused the orphaning in the first place.
