## Procedure BKP-20261005-00: Restore the Minecraft server (Pelican) from its restic backups

This procedure restores the `rimbilliton.akn` Minecraft host from its off-site backups: a Backblaze B2 restic repository
fed daily by the `minecraft` restic job (`src/infrastructure/nixos/modules/backup.nix`). It covers four cases:
inspecting snapshots, restoring one server's world, restoring the Panel data, and a full disaster recovery after losing
the VM. The steps are grounded in `modules/backup.nix`, `modules/pelican.nix`, `stack/backblaze.ts` and
`docs/BOOTSTRAP.md` of the project.

### Technical framework and conventions

How the backups are built, because it dictates every restore path:

- **Two layers.** Wings writes consistent world archives to `/var/lib/pelican/backups/<backup uuid>.tar.gz` when the
  Panel's schedule (or a manual backup) asks for it. restic then ships that directory plus `/var/lib/pelican-panel/data`
  (Panel SQLite database, `.env` with `APP_KEY`, plugins) to B2 every day at 04:30 (up to 15 minutes of random delay),
  with `Persistent = true`. One restic run produces one snapshot holding both paths.
- **Live server volumes are not backed up.** `/var/lib/pelican/volumes` (the running worlds) is not in the restic paths:
  a world only exists off-site through a Wings archive. Without Wings backups scheduled in the Panel, there is nothing
  to restore.
- **Repository**: `s3:<b2Endpoint>/<bucket>/restic`, where `b2Endpoint` and `bucket` are the values set in
  `modules/backup.nix` (`bucket` is the Pulumi output `backupsBucketName`). The bucket is private and has
  `protect: true, retainOnDelete: true` in Pulumi, so it survives a VM loss or a stack teardown.
- **Credentials**: the restic password (`restic_password`) and the B2 credentials (`restic_b2_env`, an env file with
  `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`) are SOPS secrets, decrypted on the host to `/run/secrets/`. The B2
  application key (`rimbilliton-minecraft-restic`) is scoped to this bucket and can read, write and delete files.
- **Retention**: 7 daily, 4 weekly, 6 monthly snapshots (`--keep-daily 7 --keep-weekly 4 --keep-monthly 6`).
- **Ownership**: the Panel container runs as `www-data` (`82:82`) and owns everything under
  `/var/lib/pelican-panel/data`. Wings runs with `WINGS_UID=988` / `WINGS_GID=988`.

> [!CAUTION]
>
> The restic password must be kept **outside the VM**. The secrets template says a copy lives in OpenBao. If the
> password is lost, the repository is unreadable and every backup is lost. The password is also in
> `secrets/rimbilliton.sops.yaml` (in git, encrypted for the admin age key and the host key), so the admin age key is
> the second way to get it back. Before relying on this procedure, confirm that you can retrieve it without the VM (see
> Prerequisites).

### Prerequisites

Before starting, ensure the following tools are installed and configured: `mise` (provides `sops`), `pulumi`, `ssh`, and
Docker plus `nonix` for the full disaster recovery (see `projects/rimbilliton.akn/docs/BOOTSTRAP.md`).

You must also have:

- SSH access as `root` to the host over Tailscale (SSH is Tailscale-only), except in the full disaster recovery where
  the host does not exist yet.
- The restic password, from OpenBao or from `sops -d --extract '["restic_password"]' secrets/rimbilliton.sops.yaml`
  (needs the admin age key, `SOPS_AGE_KEY_FILE`).
- The B2 credentials, from `pulumi stack output backupsKeyId` and `pulumi stack output backupsKeySecret --show-secrets`
  (stack `rimbilliton_akn.live`), or from the `restic_b2_env` SOPS secret.
- Access to the Panel as an admin (`https://minecraft.chezmoi.sh`) for scenarios 2 and 4.

### Required inputs

Export these once on the host (scenarios 1 to 3) or on a workstation (scenario 4, before the host exists):

```bash
export HOST=<tailscale hostname of the host>                           # To adapt, see BOOTSTRAP.md
export BUCKET=<value of the Pulumi output backupsBucketName>           # To adapt
export B2_ENDPOINT=<b2Endpoint value in modules/backup.nix>            # To adapt
export SNAPSHOT_ID=<restic snapshot ID, or "latest">                   # Chosen in Step 1
export SERVER_UUID=<UUID of the game server>                           # Panel > server > Settings > Debug Information
export BACKUP_UUID=<UUID of the Wings backup>                          # Panel > server > Backups, or the file name
export RESTORE_DIR=/var/tmp/restic-restore                             # Staging directory, outside the live paths
```

## Step 1 — List and inspect the snapshots (scenario 1)

Read-only. Run it on the host, as `root`.

1. Define the restic environment explicitly. This always works, whatever the wrapper situation:

   ```bash
   export RESTIC_REPOSITORY="s3:${B2_ENDPOINT}/${BUCKET}/restic"
   export RESTIC_PASSWORD_FILE=/run/secrets/restic_password
   set -a; . /run/secrets/restic_b2_env; set +a   # AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY
   command -v restic || echo "restic not on PATH"
   # → a path to restic. If "restic not on PATH", prefix every restic command below with: nix shell nixpkgs#restic -c
   ```

   > [!NOTE] Not verified
   >
   > The NixOS `services.restic.backups.<name>` module normally installs a `restic-minecraft` wrapper that pre-loads the
   > repository, password file and environment file (`restic-minecraft snapshots`). `modules/backup.nix` does not set
   > the option that controls it, so this relies on the module default of the pinned nixpkgs (`nixos-26.05`). Check with
   > `command -v restic-minecraft`; if it is absent, use the explicit variables above.

2. List the snapshots:

   ```bash
   restic snapshots
   # → one line per snapshot: ID, time, host, paths. Each lists /var/lib/pelican/backups and /var/lib/pelican-panel/data
   ```

3. Inspect one snapshot (pick `SNAPSHOT_ID` from the previous output, or use `latest`):

   ```bash
   restic ls "${SNAPSHOT_ID}" /var/lib/pelican/backups | head -50
   # → the <backup uuid>.tar.gz archives present in that snapshot
   restic ls "${SNAPSHOT_ID}" /var/lib/pelican-panel/data
   # → database/database.sqlite, .env, plugins/ ... (the exact list depends on the Panel)
   restic stats "${SNAPSHOT_ID}"
   # → total size of the snapshot
   ```

**Verification**: the most recent snapshot is less than about 25 hours old (04:30 daily plus delay). If not, check
`systemctl status restic-backups-minecraft.service restic-backups-minecraft.timer` and
`journalctl -u restic-backups-minecraft`.

## Step 2 — Restore one server's world from a Wings archive (scenario 2)

Wings archives hold one server each, named after the backup UUID. Pick the path that matches the situation: the archive
is still on the host (2a), or it only exists in B2 (2b first, then 2a).

### 2a — Through the Panel (preferred)

1. In the Panel, open the server, then Backups. Pick the backup, then Restore.
2. Choose whether to delete the existing files first ("truncate directory"). Without it, the archive is extracted over
   the current files and keeps files the archive does not contain.

   > [!NOTE] Not verified
   >
   > Whether the server must be stopped by hand before the restore, or whether Wings stops it itself, depends on the
   > Pelican version (`v1.0.0-beta38` / Wings `beta29`) and is not described in this repository. Stop the server first
   > from the Panel: it is harmless and avoids a restore over a running world.

3. Wait for the restore to finish and start the server.

**Verification**: the server console shows the world loading without errors, and a player can join. In the Panel the
backup stays listed.

### 2b — The archive is not on the host anymore: fetch it from restic

```bash
# Restore only the wanted archive into a staging directory (nothing live is touched)
mkdir -p "${RESTORE_DIR}"
restic restore "${SNAPSHOT_ID}" --target "${RESTORE_DIR}" \
  --include "/var/lib/pelican/backups/${BACKUP_UUID}.tar.gz"
ls -l "${RESTORE_DIR}/var/lib/pelican/backups/${BACKUP_UUID}.tar.gz"
# → the file exists with a plausible size

# Put it where Wings expects it, then the Panel can restore it (2a)
cp -a "${RESTORE_DIR}/var/lib/pelican/backups/${BACKUP_UUID}.tar.gz" /var/lib/pelican/backups/
```

> [!NOTE]
>
> The Panel only lists backups present in its database. If the Panel database was lost or restored from an older
> snapshot, the archive may not be listed: use 2c.

### 2c — Manual fallback: extract the archive by hand

Use it when the Panel restore fails or the backup is unknown to the Panel. The server must be stopped, so that Wings and
the game do not write while you extract.

1. Stop the server from the Panel (Stop, then wait for the state `Offline`).
2. Keep a copy of the current data, and check the archive:

   ```bash
   VOLUME=/var/lib/pelican/volumes/${SERVER_UUID}
   ls -ld "${VOLUME}"
   # → the server directory exists, with its owner (note it)
   tar -tzf "/var/lib/pelican/backups/${BACKUP_UUID}.tar.gz" | head
   # → a listing without error; the paths are relative to the server root
   mv "${VOLUME}" "${VOLUME}.pre-restore"
   mkdir "${VOLUME}"
   ```

3. Extract, then give the files back to the owner the server directory had before:

   ```bash
   tar -xzf "/var/lib/pelican/backups/${BACKUP_UUID}.tar.gz" -C "${VOLUME}"
   chown --reference="${VOLUME}.pre-restore" "${VOLUME}"
   chown -R --reference="${VOLUME}.pre-restore" "${VOLUME}"
   ls -ln "${VOLUME}" | head
   # → the files belong to the same uid:gid as ${VOLUME}.pre-restore (the Wings user, expected 988:988)
   ```

   > [!NOTE] Not verified
   >
   > The expected owner `988:988` comes from `WINGS_UID` / `WINGS_GID` in `modules/pelican.nix`; the real owner of the
   > files inside a server directory was not checked. That is why the commands copy the owner from the existing
   > directory instead of hardcoding it. If the server directory did not exist at all, create the server in the Panel
   > first and use its directory as reference.

4. Start the server from the Panel.

**Verification**: the server reaches `Running`, the world is the expected one (level name, last known build).

**Rollback**: stop the server, then `rm -rf "${VOLUME}" && mv "${VOLUME}.pre-restore" "${VOLUME}"`. Delete
`${VOLUME}.pre-restore` only once the restored world is confirmed good.

## Step 3 — Restore the Panel data (scenario 3)

Covers the SQLite database, `.env` (with `APP_KEY`) and plugins, all under `/var/lib/pelican-panel/data`. Use it when
the Panel is broken or lost its configuration. Wings stays configured from SOPS and is unaffected.

> [!IMPORTANT]
>
> `APP_KEY` encrypts sensitive values stored in the Panel database (typically API tokens and OAuth/plugin secrets).
> Restore the database and the `.env` **from the same snapshot**. A database restored with a different (or newly
> generated) `APP_KEY` leaves those values unreadable, and they have to be re-entered. There is no way to recover them
> without the original key.

> [!NOTE] Not verified
>
> The exact list of encrypted fields, and the location of `.env` inside `/var/lib/pelican-panel/data`, are not described
> in this repository (`modules/pelican.nix` mounts that directory as `/pelican-data` and sets `XDG_DATA_HOME`). Locate
> the file with `find /var/lib/pelican-panel/data -maxdepth 2 -name .env` after the restore.

1. Stop the Panel (and Wings, which depends on it) so nothing writes to the database:

   ```bash
   systemctl stop docker-pelican-wings docker-pelican-panel
   systemctl is-active docker-pelican-panel docker-pelican-wings
   # → inactive (twice)
   ```

2. Restore the Panel data from the snapshot into a staging directory:

   ```bash
   rm -rf "${RESTORE_DIR}" && mkdir -p "${RESTORE_DIR}"
   restic restore "${SNAPSHOT_ID}" --target "${RESTORE_DIR}" --include /var/lib/pelican-panel/data
   ls -la "${RESTORE_DIR}/var/lib/pelican-panel/data" "${RESTORE_DIR}/var/lib/pelican-panel/data/database"
   # → database/database.sqlite and .env are present
   ```

3. Swap the live directory for the restored one, keeping the old one:

   ```bash
   mv /var/lib/pelican-panel/data /var/lib/pelican-panel/data.pre-restore
   cp -a "${RESTORE_DIR}/var/lib/pelican-panel/data" /var/lib/pelican-panel/data
   chown -R 82:82 /var/lib/pelican-panel/data
   chmod 0770 /var/lib/pelican-panel/data /var/lib/pelican-panel/data/plugins /var/lib/pelican-panel/data/database
   ls -ldn /var/lib/pelican-panel/data /var/lib/pelican-panel/data/database/database.sqlite
   # → owner 82 82 on both (the database file is 0660 in the tmpfiles rule)
   ```

   > [!NOTE]
   >
   > The directory modes mirror the `systemd.tmpfiles.rules` of `modules/pelican.nix` (`0770` for `data`, `plugins`,
   > `database`; `0660` for the database file). `/var/lib/pelican-panel/logs` is not backed up and is left untouched.

4. Check the SQLite database before starting anything:

   ```bash
   nix shell nixpkgs#sqlite -c sqlite3 /var/lib/pelican-panel/data/database/database.sqlite 'PRAGMA integrity_check;'
   # → ok
   ```

   > [!WARNING]
   >
   > restic copies the database while the Panel may be running (the job is not stopped around the backup). A snapshot
   > taken mid-write can fail this check. If it does, repeat Steps 2 to 4 with the previous snapshot
   > (`restic snapshots`).

5. Start the Panel, then Wings:

   ```bash
   systemctl start docker-pelican-panel
   systemctl start docker-pelican-wings
   systemctl is-active docker-pelican-panel docker-pelican-wings
   # → active (twice)
   ```

**Verification**: `https://minecraft.chezmoi.sh` shows the login page (not the installer), you can sign in (Pocket-ID or
the admin account), the node is green and the servers are listed.

**Rollback**:

```bash
systemctl stop docker-pelican-wings docker-pelican-panel
rm -rf /var/lib/pelican-panel/data
mv /var/lib/pelican-panel/data.pre-restore /var/lib/pelican-panel/data
systemctl start docker-pelican-panel docker-pelican-wings
```

Delete `data.pre-restore` and `${RESTORE_DIR}` once the restore is confirmed.

## Step 4 — Full disaster recovery, the VM is lost (scenario 4)

Order matters: the restore must happen **before** the Pelican containers have run on the new host, and before the first
restic run (04:30). On a fresh host the containers start at boot, create an empty SQLite database and a new `APP_KEY`
(installer), and an empty-state backup would then be uploaded.

1. **Reprovision the infrastructure.** From `projects/rimbilliton.akn/src/infrastructure/pulumi`, following BOOTSTRAP.md
   step 1:

   ```bash
   mise run pulumi:diff && mise run pulumi:apply
   pulumi stack output backupsBucketName
   # → the same bucket as before (it is protected and retained), used as BUCKET
   ```

   > [!NOTE]
   >
   > If the Pulumi state itself is lost, the B2 bucket still holds the backups: recreate or import the stack as
   > described in `docs/procedures/infrastructure/INF-20260705-00.pulumi-state-and-import.md`, and mint a new B2
   > application key scoped to that bucket (`restic_b2_env`). Do not let Pulumi create a second bucket.

2. **Reinstall NixOS** with BOOTSTRAP.md steps 3 and 4 (host key, SOPS file, `nixos-anywhere` through `nonix`). Keep the
   same `restic_password` as before: a new value cannot open the existing repository.

   > [!IMPORTANT]
   >
   > sops-nix decrypts with the host SSH key. If you generate a new host key (BOOTSTRAP step 3), its age key must be a
   > recipient of `secrets/rimbilliton.sops.yaml`: replace the old host key in
   > `projects/rimbilliton.akn/src/infrastructure/nixos/.sops.yaml`, then run `sops updatekeys` on the file before the install. If you still have the previous
   > `extra/etc/ssh/ssh_host_ed25519_key`, reusing it avoids that.

3. **Stop everything Pelican-related and the backup job**, as soon as the host is reachable over Tailscale:

   ```bash
   ssh root@"${HOST}" 'systemctl stop docker-pelican-wings docker-pelican-panel restic-backups-minecraft.timer'
   ssh root@"${HOST}" 'systemctl is-active docker-pelican-panel docker-pelican-wings restic-backups-minecraft.timer'
   # → inactive (three times)
   ```

   Wings has no valid node configuration yet and restarts in a loop until Step 4.6, which is expected.

4. **Restore from restic.** On the host (`ssh root@"${HOST}"`), define the environment and run:

   ```bash
   export RESTIC_REPOSITORY="s3:${B2_ENDPOINT}/${BUCKET}/restic"
   export RESTIC_PASSWORD_FILE=/run/secrets/restic_password
   set -a; . /run/secrets/restic_b2_env; set +a
   restic snapshots
   # → the snapshots of the previous host (the hostname is the same, so they are listed together)
   ```

   Then restore both paths from the chosen snapshot, replacing what the fresh install created:

   ```bash
   rm -rf "${RESTORE_DIR}" && mkdir -p "${RESTORE_DIR}"
   restic restore "${SNAPSHOT_ID}" --target "${RESTORE_DIR}"
   rm -rf /var/lib/pelican-panel/data
   cp -a "${RESTORE_DIR}/var/lib/pelican-panel/data" /var/lib/pelican-panel/data
   chown -R 82:82 /var/lib/pelican-panel/data
   cp -a "${RESTORE_DIR}/var/lib/pelican/backups/." /var/lib/pelican/backups/
   nix shell nixpkgs#sqlite -c sqlite3 /var/lib/pelican-panel/data/database/database.sqlite 'PRAGMA integrity_check;'
   # → ok
   ls /var/lib/pelican/backups | head
   # → the <backup uuid>.tar.gz archives
   ```

   Apply the permission details of Step 3 (modes, ownership check) as well.

5. **Wings credentials.** The three values `wings_uuid`, `wings_token_id` and `wings_token` belong to the node stored in
   the restored database. They are not in the restic backups: they live in `secrets/rimbilliton.sops.yaml` (in git).
   - If that file still holds them, they are already in place: nothing to do.
   - If they are lost, start the Panel alone (`systemctl start docker-pelican-panel`), sign in, open the node's
     Configuration tab, reset the token if needed, and copy only `uuid`, `token_id` and `token`:

     ```bash
     cd projects/rimbilliton.akn/src/infrastructure/nixos
     sops secrets/rimbilliton.sops.yaml   # set wings_uuid, wings_token_id, wings_token
     mise run nixos:oci:update
     # → the switch succeeds (same task as BOOTSTRAP.md step 6.3)
     ```

6. **Start the services and re-enable the backup timer:**

   ```bash
   ssh root@"${HOST}" 'systemctl start docker-pelican-panel docker-pelican-wings restic-backups-minecraft.timer'
   ssh root@"${HOST}" 'systemctl is-active docker-pelican-panel docker-pelican-wings restic-backups-minecraft.timer'
   # → active (three times)
   ```

7. **Check in the Panel**: the node is green, the servers are listed, and their Backups tab lists the archives. Then
   restore each world with Step 2 (the live volumes were not backed up, see below).

**Verification**: all of the above, plus `restic snapshots` after the next 04:30 run shows a new snapshot containing the
restored data.

### What is not in the restic backups

| Item                                                                              | Where it comes from                                                                                                                                                               |
| --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wings `config.yml` and node token (`wings_uuid`, `wings_token_id`, `wings_token`) | SOPS file in git (`secrets/rimbilliton.sops.yaml`), rendered by sops-nix; or reset from the Panel (Step 4.5)                                                                      |
| `restic_password`, `restic_b2_env`, `tailscale_authkey`                           | SOPS file in git; the restic password also in OpenBao; B2 key from Pulumi outputs                                                                                                 |
| Live server volumes `/var/lib/pelican/volumes`                                    | Not backed up. Only the Wings archives are: restore each world through Step 2. Anything newer than the last archive is lost                                                       |
| Panel logs `/var/lib/pelican-panel/logs`                                          | Not backed up, not needed                                                                                                                                                         |
| Pocket-ID group `minecraft` and OIDC client `Minecraft`                           | Created by hand in Pocket-ID (BOOTSTRAP.md step 2), outside this host: they survive the VM loss                                                                                   |
| Pocket-ID plugin and sign-in settings                                             | Declared in NixOS: the plugin is fetched by Nix and installed by `pelican-plugins`, the client ID and secret are the `oauth_pocketid_*` SOPS secrets (in git). Nothing to restore |

> [!NOTE]
>
> The plugin and its OAuth settings are rendered from NixOS and SOPS, not from the Panel database. After the restore,
> start `pelican-plugins` (`systemctl restart pelican-plugins`) if Settings > OAuth does not show Pocket ID. If the
> Pocket-ID client had to be recreated, update the `oauth_pocketid_*` secrets and its callback URL as in BOOTSTRAP.md
> step 2.

## Step 5 — Restore test routine

A backup that was never restored is a hope. Quarterly, and after any change to `backup.nix`, the Pelican image tags or
the B2 key, run on the host:

```bash
# 1. The job runs and the repository is consistent
systemctl status restic-backups-minecraft.timer --no-pager
restic snapshots --latest 3
restic check
# → the timer is active, the last snapshot is recent, "no errors were found"

# 2. Restore the Panel data and the newest archive into a scratch directory, never over the live paths
rm -rf "${RESTORE_DIR}" && mkdir -p "${RESTORE_DIR}"
restic restore latest --target "${RESTORE_DIR}"
nix shell nixpkgs#sqlite -c sqlite3 "${RESTORE_DIR}/var/lib/pelican-panel/data/database/database.sqlite" 'PRAGMA integrity_check;'
# → ok
LAST=$(ls -t "${RESTORE_DIR}"/var/lib/pelican/backups/*.tar.gz | head -1)
tar -tzf "${LAST}" > /dev/null && echo "archive OK"
# → archive OK
rm -rf "${RESTORE_DIR}"
```

What to check besides the commands:

- `.env` exists in the restored Panel data and contains an `APP_KEY` line (check the line exists, do not print its
  value).
- The newest archive in the Panel's Backups tab matches a file in the restore.
- Once a year, perform a real world restore (Step 2c) on a throwaway server, and confirm that the restic password can be
  retrieved from OpenBao without the VM.

## Troubleshooting

| Symptom                                                              | Cause and fix                                                                                                                     |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `wrong password or no key found`                                     | The password file does not match the repository. Use the copy from OpenBao. If it is lost, the backups are unrecoverable          |
| `Fatal: unable to open config file ... 401` / `403` / `AccessDenied` | Wrong or revoked B2 key. Re-read `backupsKeyId` / `backupsKeySecret` from Pulumi (key must be scoped to this bucket)              |
| `Fatal: repository does not exist`, or `NoSuchBucket`                | Wrong `BUCKET` or `B2_ENDPOINT`. Compare with `pulumi stack output backupsBucketName` and `modules/backup.nix`                    |
| `unable to create lock` / `repository is already locked`             | A backup or prune is running (`systemctl status restic-backups-minecraft`). Wait. Use `restic unlock` only if no job runs         |
| Panel shows the installer after a restore                            | The restored data was overwritten by a fresh install or is in the wrong place. Redo Step 3, check `data/database/database.sqlite` |
| `500` error or login failure after restoring Panel data              | `.env` / `APP_KEY` and database come from different snapshots, or ownership is not `82:82`. Redo Step 3 from a single snapshot    |
| `PRAGMA integrity_check` is not `ok`                                 | The snapshot caught the database mid-write. Restore the previous snapshot                                                         |
| Node stays red, Wings restarts in a loop                             | The three Wings values are missing or stale in SOPS. Reset the token in the Panel, update SOPS, `nixos-rebuild switch` (Step 4.5) |
| Backup listed in the Panel but restore fails                         | The archive is missing from `/var/lib/pelican/backups`. Fetch it with Step 2b                                                     |
| Server data not writable after a manual extract                      | Wrong owner. Re-run the `chown --reference` commands of Step 2c                                                                   |
| `command not found: restic` or `restic-minecraft`                    | Use `nix shell nixpkgs#restic -c restic ...` with the explicit variables of Step 1                                                |
