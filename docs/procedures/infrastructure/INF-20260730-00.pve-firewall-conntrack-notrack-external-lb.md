## Procedure INF-20260730-00: Exempting Cilium external LB pools from PVE firewall conntrack (NOTRACK)

This procedure documents a `pve-01` host-level fix required for the dual-NIC Talos design (ADR-014): without it, real
external clients (anything outside the homelab's Kubernetes clusters) cannot reach a cluster's Cilium external
LoadBalancer/Gateway IP, even though the request itself arrives fine and Cilium answers it correctly internally.

### Symptom

A client on VLAN 2 (Home) or any other VLAN reaches a cluster's external Gateway VIP (e.g. `10.0.0.64`, rhodes.akn) and
the TCP handshake never completes — the SYN arrives, but no SYN-ACK ever comes back. From inside the cluster (hairpin
from a pod, or a `curl` run in the node's own network namespace) the same VIP works perfectly. Only genuinely external
clients are affected.

### Root cause

The Talos dual-NIC design (ADR-014) has `eth0` (VLAN 5 trunk, no IP — Cilium L2 announcement only) and `eth1`
(`talosnet`, the SDN VNet, the node's only real IP and only default route). The client's SYN arrives on `eth0` (bridged
directly onto VLAN 5, `vmbr1`, by `pve-01`) and is handled correctly by Cilium/Envoy. The reply (SYN-ACK), however, is
generated by a userspace process (the Gateway API's embedded Envoy, bound to `127.0.0.1`) — L2 announcements only
control ARP for the VIP, not which interface the kernel picks for a socket-originated reply
([cilium/cilium#40521](https://github.com/cilium/cilium/issues/40521) confirms this directly). The reply therefore
follows the node's only default route, out `eth1`/`talosnet`, and is forwarded by `pve-01` onward toward VLAN 5 via
`vmbr0` (`ip_forward` is enabled on both `talosnet` and `vmbr0`, and there is no route/firewall rule that would
otherwise block it).

The actual failure is one layer below that: `pve-01`'s own firewall (`pve-firewall`, PVE's integrated
iptables/conntrack-based firewall) assigns a dedicated **conntrack zone** to any traffic entering through a per-guest
firewall bridge shim (`fwbr<vmid>i<net>`, created whenever a guest NIC has `firewall=1`):

```sh
# raw table, PREROUTING chain
-A PREROUTING -i fwbr+ -j CT --zone 1
```

The client's original SYN (bridged via `vmbr1` into the Talos VM's `eth0`) is evaluated in that zone. The reply (routed
via `talosnet` → `vmbr0`, never touching a `fwbr+` interface) is evaluated in the default zone instead — from that
zone's point of view it is an orphan SYN-ACK with no matching tracked connection, so PVE's own `PVEFW-FORWARD` chain
drops it as `ctstate INVALID` (its first rule, applied before anything user-configurable):

```sh
# filter table, PVEFW-FORWARD chain, rule 1 (fixed, not configurable via cluster.fw/security groups)
-A PVEFW-FORWARD -m conntrack --ctstate INVALID -j DROP
```

This was confirmed empirically: the DROP rule's packet counter incremented by exactly the number of SYN-ACK
retransmissions during each failed test, and capturing on `pve-01`'s `talosnet` interface showed the SYN-ACK arriving
there but never reaching `vmbr0`.

> [!NOTE] **Why 9 identical-looking `CT --zone 1` rules exist.** `iptables -t raw -S` on `pve-01` shows this same rule
> repeated 9 times. This is not reload/restart duplication (`pve-firewall` had 0 restarts at the time this was found) —
> it is one rule generated per currently-running guest with `firewall=1` on its `vmbr1` interface (verified: exactly 9
> such guests — LXCs `101`–`105`, VMs `109`, `201`, `2022100`, `2411000`). PVE's rule generator emits one rule per
> firewalled bridge port rather than a single deduplicated wildcard rule; since the match pattern (`fwbr+`) is identical
> every time, the 9 copies are functionally redundant with each other but not evidence of a bug.

Because `PVEFW-FORWARD`'s INVALID-drop rule is a fixed PVE baseline (evaluated before any `cluster.fw`/security-group
rule), it cannot be worked around by adding a normal firewall ACCEPT rule — those are inserted later in the chain.

### Fix: NOTRACK for the LB pool, in the raw table

Bypass conntrack entirely for the cluster's external LB pool CIDR, in both directions, so no `ctstate` classification —
valid or invalid — can ever apply to it. `raw`/`PREROUTING` is evaluated by the kernel before conntrack assigns any zone
or state, and is not managed by `pve-firewall` (only the `filter`-table `PVEFW-*` chains and the CT-zone rules in `raw`
are), so a manually-added `NOTRACK` rule here is not at risk of being overwritten by a firewall reload.

```sh
iptables -t raw -I PREROUTING 1 -d 10.0.0.64/29 -j NOTRACK   # rhodes.akn external LB pool
iptables -t raw -I PREROUTING 1 -s 10.0.0.64/29 -j NOTRACK
```

To persist across reboots and `ifreload -a` (which runs on every `pvesh set /cluster/sdn`, i.e. every future SDN
change), install this as an idempotent `/etc/network/if-up.d/` hook — the same class of mechanism `ifupdown2` already
uses for PVE's own generated rules, guarded to fire once per reload rather than once per interface:

```sh
# /etc/network/if-up.d/99-talosnet-lb-notrack
#!/bin/sh
# Exempt each cluster's Cilium external LB pool from conntrack, so replies to
# L2-announced VIPs (dual-NIC Talos setup, ADR-014) aren't misclassified as
# ctstate INVALID by PVEFW-FORWARD. The reply leaves via talosnet/vmbr0,
# never through a fwbr+ interface, so it never gets the CT zone 1 tag PVE
# assigns to firewalled VM/CT bridge traffic -- from that mismatched zone's
# view it looks like an orphan SYN-ACK, which PVEFW-FORWARD's first rule
# drops as INVALID. NOTRACK sidesteps conntrack entirely for this traffic so
# no ctstate check can apply. Runs on every ifreload (incl. SDN applies);
# guarded on $IFACE=lo so it fires once per reload, not once per interface.
[ "$IFACE" = "lo" ] || exit 0

for pool in 10.0.0.64/29; do  # rhodes.akn external LB pool; add future clusters' pools here
  iptables -t raw -C PREROUTING -d "$pool" -j NOTRACK 2>/dev/null || \
    iptables -t raw -I PREROUTING 1 -d "$pool" -j NOTRACK
  iptables -t raw -C PREROUTING -s "$pool" -j NOTRACK 2>/dev/null || \
    iptables -t raw -I PREROUTING 1 -s "$pool" -j NOTRACK
done
```

```sh
scp 99-talosnet-lb-notrack root@pve-01.pve.chezmoi.sh:/etc/network/if-up.d/99-talosnet-lb-notrack
ssh root@pve-01.pve.chezmoi.sh chmod +x /etc/network/if-up.d/99-talosnet-lb-notrack
```

> [!NOTE] Adding a future cluster's LB pool: append its CIDR to the `for pool in ...` list and re-run the script (or
> just wait for the next `ifreload`/reboot).

### Verification

```sh
# From outside the homelab clusters entirely (e.g. a laptop on VLAN 2):
curl -m 5 --resolve <hostname>:443:<cluster-external-lb-ip> https://<hostname>/

# On pve-01, confirm the NOTRACK rules are present and exactly 2 (no duplicates):
iptables -t raw -L PREROUTING -n --line-numbers | grep NOTRACK

# Confirm they survive a real reload (this is what every SDN apply triggers):
ifreload -a
iptables -t raw -L PREROUTING -n --line-numbers | grep NOTRACK   # still exactly 2
```

Verified on `rhodes.akn`'s external Gateway (`10.0.0.64/29`) on 2026-07-30: `HTTP/1.1 200 OK` from a real client on VLAN
2, before and after a live `ifreload -a`.

### Notes and troubleshooting

- **This is a `pve-01` host-level fix, not something expressible in this repo's Pulumi/Ansible today.** No existing
  automation manages `pve-01`'s own OS-level config (Pulumi's `@pulumi/proxmox` provider has no per-source NAT/conntrack
  exception primitive; `catalog/ansible/` has no role for `pve-01` itself, only guest-level roles like `truenas`). This
  procedure is the source of truth until/unless that changes.
- **SNAT is not actually active on `talosnet` today**, despite `sdn.ts` declaring `snat: true` and this being documented
  as mandatory in [INF-20260627-00](INF-20260627-00.proxmox-sdn-setup.md) — live inspection during this investigation
  (`pvesh get /cluster/sdn/vnets/talosnet/subnets`) showed no `snat` key at all, and `iptables -t nat -L POSTROUTING`
  was empty. This is a separate drift between declared and live state, not something this procedure fixes — flagged here
  since it was discovered along the way, not yet filed as its own issue.
- If a future cluster's external Gateway shows the same symptom, add its LB pool CIDR to the script's `for pool in ...`
  list rather than writing a new rule from scratch.
